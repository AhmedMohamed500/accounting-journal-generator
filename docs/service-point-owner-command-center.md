# FINORA Service Point — Owner Command Center

## الهدف

تحويل لوحة صاحب المحل من عرض أرقام إلى مساحة قرار يومية تعمل بالكامل فوق بيانات Service Point المحلية الحالية. لا تضيف هذه المرحلة Backend أو Database أو AI API أو خدمة مدفوعة، ولا تدّعي مزامنة أو تنبيهًا عن بُعد.

المسارات:

- `/ar/service-point/owner-dashboard`
- `/en/service-point/owner-dashboard`

## تجربة المالك

تبدأ الشاشة بستة مؤشرات فوق الطي: ربح اليوم، حجم وعدد العمليات الناجحة، الخزنة، أرصدة الخدمات، العمليات المعلقة، والفروق غير المحسومة. يمكن إخفاء القيم عند مشاركة الشاشة والتبديل بين:

- **Quick:** لقطة اليوم، Smart Daily Brief، القرارات ذات الأولوية، وخريطة السيولة.
- **Detailed:** يضيف مقارنة اليوم بأمس، آخر 7 أيام بالفترة السابقة، لقطة الشهر، ترتيب الربحية، أداء الكاشير، ومقارنة المحلات عند توافر أكثر من محل.

زر **نسخ الملخص** يستخدم Clipboard API ثم `execCommand` كـfallback. زر **طباعة / PDF** يعرض تقرير A4 نظيفًا عبر نافذة الطباعة في المتصفح؛ اختيار “Save as PDF” يتم من المتصفح نفسه.

## محرك التوصيات

المحرك داخل `lib/pos/recommendations.ts` حتمي وقابل للاختبار. لا يستخدم نموذجًا لغويًا. المدخلات هي الورديات والعمليات واللقطة الحالية والإعدادات والباقة والتاريخ. المخرجات موحدة وفيها النوع والخطورة والأولوية والعنوان والتفسير والإجراء والرابط المقترح.

الأنواع المدعومة:

- `LOW_SERVICE_BALANCE`
- `IDLE_SERVICE_BALANCE`
- `HIGH_CASH_EXPOSURE`
- `SHIFT_DIFFERENCE`
- `PENDING_TOO_LONG`
- `FAILED_OPERATION_SPIKE`
- `DUPLICATE_RISK`
- `LOW_MARGIN_PROVIDER`
- `HIGH_MARGIN_PROVIDER`
- `CASHIER_DIFFERENCE_RISK`
- `PROFIT_DROP`
- `PROFIT_IMPROVEMENT`
- `BACKUP_OVERDUE`
- `TRIAL_ENDING`

كل الحدود التجارية قابلة للتعديل مركزيًا في `data/service-point-owner-config.ts`: حد الرصيد المنخفض، سيولة الرصيد الراكد، تعرض الخزنة، فروق الورديات، عمر المعلقة، ارتفاع الفشل، الهوامش، تغير الربح، ونهاية التجربة.

### إضافة قاعدة جديدة

1. أضف النوع إلى `OwnerRecommendationType` في `types/pos-owner.ts`.
2. أضف الحد القابل للضبط إلى `servicePointOwnerConfig` بدل وضع رقم داخل الـComponent.
3. استخدم البيانات المجمعة الموجودة أو helpers مثل `isEffectivePosOperation` و`calculateProviderPerformance` و`calculateCashierPerformance`.
4. أنشئ Recommendation عربية/إنجليزية بسبب واضح وإجراء ورابط و`priority`.
5. أضف اختبارًا للشرط الإيجابي، والحالة التي لا يجب أن تُنتج تنبيهًا.

الأولوية رقم من 0 إلى 100، ثم تُستخدم الخطورة لكسر التعادل. `critical` محجوز للفشل المتكرر أو فرق/خطر مالي يتجاوز الحد الحرج، ثم `high` و`medium` و`low`. الإشارات الإيجابية تستخدم `positive` وتظهر بعد المخاطر؛ الهدف أن يرى المالك القرارات العاجلة أولًا دون إخفاء الفرص.

## الحسابات والمقارنات

- العملية الفعالة هي الناجحة وغير المرتدة، باستخدام `isEffectivePosOperation` الموجود.
- المعلقة والفاشلة لا تدخل في الحجم أو الإيراد أو التكلفة أو الربح.
- المقارنات تعتمد `businessDate` وتستخدم فترات `[from, to)` لتجنب التكرار بين الأيام.
- عند كون الفترة السابقة صفرًا، ترجع نسبة التغير `null` وتعرض الواجهة “لا توجد قاعدة مقارنة” بدل القسمة على صفر أو نسبة مضللة.
- ترتيب مقدمي الخدمة افتراضيًا بصافي الربح، مع خيار الهامش.
- ترتيب المحلات بصافي الربح ثم حجم الحركة.

## صياغة أداء الكاشير

التصنيفات: Excellent / Stable / Needs Review. هي إشارات تشغيلية للمراجعة والدعم وليست حكمًا أو اتهامًا. تعتمد على فرق التسوية والفشل والمعلقة، وتعرض إجراءً مهنيًا مثل مراجعة المستندات والأرصدة بهدوء.

## الباقات

- **Starter:** الملخص والمؤشرات وSmart Daily Brief الأساسي والمقارنات الأساسية.
- **Pro:** التوصيات التنفيذية وخريطة السيولة وأداء الكاشير والتنبيهات.
- **Business:** مقارنة المحلات والمؤشرات المتقدمة عبر الفروع.

الـgating مرئي وتجريبي داخل الواجهة، وليس حماية أمنية؛ `localStorage` قابل للتعديل. التفعيل الحقيقي والصلاحيات الآمنة يحتاجان Backend.

## Sales Demo Story

بيانات العرض تنشئ محلًا منفصلًا وتقدم قصة قابلة للشرح أمام العميل:

- رصيد فوري قريب من النفاد بعد حركة جيدة.
- رصيد Vodafone Cash كبير وحركته محدودة، فيظهر كسيولة راكدة.
- كاشير حالي مستقر تشغيليًا.
- وردية أمس بفارق نقدي صغير 18 ج.م دون صياغة اتهامية.
- عمليتان معلقتان، إحداهما تجاوزت ساعة فتظهر كقرار ذي أولوية.

`Reset Sales Demo` يحذف محل العرض فقط ولا يلمس بيانات العميل.
